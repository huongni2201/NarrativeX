# Chapter-first continuation workflow — V1.11

Chapter là processing boundary bền vững của baseline V1.11. Project có thể nhận thêm hoặc sửa một Chapter mà không mặc định phân tích/generate/render lại các Chapter không bị ảnh hưởng. Tạo Project chỉ tạo metadata; AI analysis chỉ bắt đầu khi một Chapter đã được persist và user chủ động yêu cầu Analyze.

## Flow

```text
Authenticated owner
  -> Create Project metadata only
  -> create/edit/reorder Chapter with If-Match
  -> persist Chapter source/snapshot
  -> resolve source StoryVersion and affected scope
  -> snapshot Project Bible, locked CharacterVersion, Location, Style and generation settings
  -> persist Chapter DRAFT + inherited snapshot hash
  -> explicit Analyze Chapter
  -> CHAPTER_ANALYZE
  -> optional downstream generation/production planning for affected scope
  -> chapter audio/visual readiness
  -> backend-authorized local project render when requested
  -> durable progress + terminal notification
```

The current HTTP analysis contract is:

```http
POST /api/v1/projects/{projectId}/chapters/{chapterId}/analysis-jobs
```

The endpoint performs ownership, saved-source, idempotency, entitlement/quota and cost admission, then persists the durable job/stage/outbox boundary before worker execution. After commit, outbox bookkeeping is finalized independently; Python workers discover and claim actual work directly from PostgreSQL using polling/lease queries. Redis, a broker, `LISTEN`, and `NOTIFY` are not required by this flow.

## Rules

- `Create Project` never triggers AI analysis, image generation, TTS, render or another paid AI/media operation.
- Chapter source text, StoryVersion relation, order and metadata are versioned/optimistically locked. A stale `If-Match` returns `409 CONFLICT` and never silently overwrites newer data.
- Analysis/re-analysis is scoped to the persisted Chapter explicitly submitted by the user.
- Expensive work pins Chapter source identity (`chapterId`, `rowVersion`, `sourceHash`) so stale results cannot silently overwrite changed source.
- A continuation may inherit a snapshot rather than a live pointer to mutable project settings when the corresponding workflow supports it. Existing reviewed/generated history must remain reproducible when project settings later change.
- Affected-scope regeneration is the intended direction: unchanged approved assets should be reusable rather than regenerated by default.
- Chapter/job progress is persisted by stage; reconnect or worker restart recovers durable work and does not create a duplicate paid submission.

## Safety and cost gates

Prompt-injection boundaries, account abuse checks, applicable real-person consent, entitlement and operation/cost admission run before expensive Chapter work. Provider safety policy remains in force during provider execution. A job with ambiguous external submission remains `UNKNOWN` and reconciles before retry.

## Current foundation status

Implemented foundations include Chapter/Scene/VisualBeat persistence, durable Chapter Analyze, create/edit/import commands, owner-scoped Chapter-creation idempotency, durable enqueue, worker PostgreSQL claim/lease/heartbeat, stale-source protection and generation status recovery.

Current analysis also materializes richer Character profile/appearance data and beat-specific Character participation. Exact deterministic VisualBeat source offsets and source-to-audio timing reconciliation remain active timing work rather than a completed continuation capability.

Full affected-scope continuation/regeneration, complete continuity-aware inheritance, broader full-project continuation orchestration and richer resume/review UX remain follow-up work tracked in `../product/ROADMAP.md`.
