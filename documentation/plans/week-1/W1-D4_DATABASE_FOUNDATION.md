# W1-D4 — PostgreSQL and Flyway Foundation

## Objective

Establish a production-safe persistence baseline for identity, workspace ownership and the existing Project/Story foundation. PostgreSQL is canonical; Redis and object storage never replace relational business state.

> **Implementation prerequisite:** activate the repository's `spring-data-jpa` skill before adding or modifying any entity, repository or projection. Entity mappings, migrations and tests must be reviewed together; any deviation requires developer approval.

## Existing schema assessment

The repository now contains one consolidated baseline:

- `V1__initial_schema.sql`: schema marker, projects, stories, chapters, scenes, visual beats, jobs, stage/provider operations, operation plans, rights, moderation, notifications/outbox, entitlement/usage, identity privacy, AI audit, deletion, abuse, reusable character identity, appearances, assignments and keyset pagination.
- JPA `AuditedEntity` using `BIGINT IDENTITY`, `row_version`, `created_at` and `updated_at`.

This baseline was consolidated before any data or migration history existed in a shared environment. Do not edit it after release; future corrections must use a new forward migration.

## P0 decision: identifier strategy

The Week 1 timeline requests UUID while current tables/entities use internal `BIGINT IDENTITY`; user IDs are strings and generation jobs also have a string UUID. Before changing identifiers:

- [ ] Inventory all API-visible IDs, FKs, fixtures and frontend types.
- [ ] Choose one documented strategy: UUID primary keys, or internal BIGINT keys plus immutable opaque public UUIDs.
- [ ] Prefer UUID/public IDs when opacity and cross-system identity are required; do not store UUID as `VARCHAR(36)` when PostgreSQL `uuid` is chosen.
- [ ] Record the choice, rollout and compatibility impact in an ADR.
- [ ] Do not perform a broad PK migration inside an unrelated task.

## Week 1 target model

Implement only the identity and ownership foundation needed to secure existing resources:

```text
app_user
  1 -> * external_identity
  1 -> * workspace_membership * -> 1 workspace
workspace
  1 -> * project
project
  1 -> * story_version
```

If v1.7 chooses single-owner projects for the first release, retain a workspace/membership-compatible model rather than duplicating authorization logic in every table. Future character/asset/render tables must inherit the same tenant scope.

## PostgreSQL design rules

- Use unquoted `snake_case` names.
- Use `timestamptz`, `text`, `boolean`, `numeric` for exact money and native `uuid` when UUID is selected.
- Business statuses use `text` plus constraints or lookup data when values will evolve; avoid a PostgreSQL enum that makes rollout brittle.
- Add `not null` for required facts and row-local `check` constraints for progress, non-negative cost, date ranges and stable state values.
- Add an explicit index for every FK/access path used by ownership queries; PostgreSQL does not create FK indexes automatically.
- Use `on delete restrict` by default for business history. Project deletion is durable soft-delete plus lifecycle cleanup, not a broad cascade.
- Normalize core relations. JSONB is limited to versioned optional/provider metadata with shape checks and access-path-specific indexes.
- Store binary assets outside PostgreSQL; persist only private storage metadata, checksum, validation and lifecycle state when the asset module arrives.

### 2. Add identity/workspace ownership schema

**Candidate tables/columns (final names follow the ADR and module language):**

- `app_users`: stable ID, email/display fields, locale, status, timestamps, row version.
- `external_identities`: user FK, provider, provider subject, safe claim metadata, timestamps; unique `(provider, subject)`.
- `workspaces`: stable ID, name/status, timestamps, row version.
- `workspace_memberships`: workspace/user FKs, role/status, timestamps; unique `(workspace_id, user_id)`.
- `projects.workspace_id`: required tenant scope after a safe backfill; retain owner attribution as required by product policy.

- [ ] Use expand/backfill/validate/contract steps for required columns on existing data.
- [ ] Seed only deterministic local/test identities; never seed production users or tokens.
- [ ] Add composite indexes that serve `workspace + status/order` access paths.
- [ ] Decide whether database RLS is defense-in-depth; application ownership checks remain mandatory either way.
- [ ] Map OIDC provider/subject, never Google access/refresh tokens, as durable identity.

### 3. Validate audit, concurrency and immutability

- [ ] Use `row_version` on mutable aggregates and map it with JPA `@Version`.
- [ ] Ensure timestamps are UTC `timestamptz` and controlled consistently by application/database policy.
- [ ] Test a stale update produces an optimistic conflict and is mapped to HTTP `409`.
- [ ] Prevent in-place updates to immutable locked/approved/render/provider snapshots through application rules and tests.
- [ ] Keep soft delete only for lifecycle entities such as Project; use `archived_at`/`deleted_at` with documented query semantics.

### 4. Prove recovery properties

- [ ] Migrate an empty PostgreSQL 16 database to latest.
- [ ] Run migrations twice and verify the second startup is clean.
- [ ] Run Hibernate `ddl-auto=validate` against PostgreSQL.
- [ ] Insert tenant/project/story fixtures and prove FK/unique/check constraints reject invalid rows.
- [ ] Flush Redis and prove all canonical fixtures remain queryable.
- [ ] Document local reset separately from production backup/PITR policy.

## Test matrix

| Test | Expected result |
|---|---|
| Empty DB -> latest Flyway | success |
| Latest DB -> restart | no schema changes/errors |
| Duplicate OIDC `(provider, subject)` | rejected |
| Duplicate workspace membership | rejected |
| Project without valid workspace | rejected after migration contract phase |
| Invalid progress/cost/order | rejected by DB and application validation |
| Stale `row_version` update | `409` through API |
| Redis flush | no loss of user/workspace/project/story state |
