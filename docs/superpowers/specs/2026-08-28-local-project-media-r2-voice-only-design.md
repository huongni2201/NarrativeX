# Local Project Media + R2 Voice-Only Storage Design

Date: 2026-08-28
Status: approved direction, hard cutover before deployment

## Goal

Make NarrativeX local-first for all project media while keeping Cloudflare R2 only for account-owned voice reference/custom voice assets.

There is no deployed production data to migrate. Existing R2 project media is treated as disposable test data, so the implementation must not retain compatibility or migration code for it.

## Storage Boundaries

### Project media

All project working and generated media is local filesystem data:

- generated narration audio;
- imported project audio;
- generated visual-beat images;
- Gemini Web generated images;
- character/portrait images;
- imported images and video;
- render intermediates;
- final rendered artifacts.

PostgreSQL stores durable identities, job state, checksums, sizes, content metadata, and logical/relative storage keys. Absolute host/container paths must not be persisted in PostgreSQL.

Project media must never be uploaded to R2 as part of the normal workflow.

### Voice reference/custom voice

R2 is reserved for reusable account-owned voice reference assets only.

Voice assets remain backend-authorized and account scoped. A narration request may reference only an owned, READY voice-reference asset. The worker downloads that voice reference from R2 into a temporary local workspace, prepares/enrolls it for VieNeu, and discards the temporary copy after the job.

R2 keys for voice assets must be account-scoped rather than using a generic project-media namespace. New uploads must use a `voices/<account-id>/...` namespace (or an equivalent opaque account-scoped prefix generated by the backend).

## Runtime Dependencies

Narration must have two separate storage dependencies:

1. `project_media_storage`: local-only storage for narration output and any project-local narration materialization.
2. `voice_reference_storage`: R2-backed read access for custom voice/reference assets.

The same storage object must not be reused for both responsibilities.

Image generation must use local project media storage only. It must not choose R2 based on a generic `MEDIA_STORAGE_MODE` flag.

Local project-media behavior is not optional in this architecture. Configuration may choose the local root, but not switch project output back to R2.

## Configuration

Replace the ambiguous shared media-storage configuration with explicit intent:

- `PROJECT_MEDIA_LOCAL_DIR` — filesystem root used by workers for generated project media.
- R2 configuration remains for voice-reference storage only.

Remove or deprecate runtime branches where `MEDIA_STORAGE_MODE=r2` causes narration/image/project output to use R2. No compatibility fallback is required.

If existing tests require an in-memory storage implementation, retain it as a test dependency only; production project-media selection must remain local-only.

## Voice Upload Flow

Desktop custom voice upload keeps the existing native picker + backend-authorized upload flow:

1. Desktop selects MP3/WAV and computes size/checksum.
2. Backend creates a voice-reference upload intent for the authenticated account.
3. Backend issues a presigned R2 upload URL under the account-owned voice namespace.
4. Desktop uploads directly to R2.
5. Backend finalizes and validates the object.
6. The resulting media/voice-reference asset is owned by the authenticated account and becomes usable only after READY validation.

Generic project-media upload intents must not remain the route for normal project media.

## Local Project Media Flow

Generated narration:

1. Worker claims narration job from PostgreSQL.
2. If a custom voice is selected, download the account-owned reference from R2 into the temporary job workspace.
3. VieNeu synthesizes locally.
4. Worker validates/alignment-checks the result.
5. Final `chapter.mp3` is persisted via local project media storage.
6. PostgreSQL records logical storage identity/checksum/duration/alignment metadata.

Generated images:

1. Worker/provider generates or retrieves the output.
2. Output is materialized directly into local project media storage.
3. PostgreSQL records logical key/checksum/dimensions/provider metadata.

Desktop/imported media continues through local native-file inspection and commit flows. It is not uploaded to R2 solely for local processing.

## Media Validation

Keep media validation logic, but separate its execution by boundary:

- voice-reference uploads on R2 retain durable validation before becoming READY;
- local project-media imports are validated during local inspect/commit/materialization;
- do not enqueue a project-media R2 validation job only to download the same asset back to the local machine.

The existing durable media-validation worker may remain only insofar as it is needed for R2 voice-reference validation. Its naming/configuration should make that responsibility explicit enough to avoid future reuse for project media.

## Cleanup

Because this is a pre-deployment hard cutover:

- remove R2 project-media production branches;
- remove misleading logs such as local narration reporting an R2 upload;
- remove dead `MEDIA_STORAGE_MODE` project-output configuration and tests that assert R2 project media;
- update documentation and compose/env examples;
- keep R2 primitives needed by backend voice upload/finalization and worker voice-reference download;
- keep local/in-memory storage primitives needed by project execution/tests.

Do not add migration, fallback, dual-write, or legacy-read behavior.

## Concurrency and Queues

This storage change does not alter the PostgreSQL durable generation queue contract. Analysis, image, and narration concurrency remain independently tunable. Storage separation must not introduce a client-side queue or duplicate scheduler.

## Error Handling

- Missing/unreadable R2 voice reference: narration job fails or retries according to existing transient/permanent infrastructure classification.
- Local project-media write failure: narration/image job uses existing local infrastructure retry/failure semantics.
- Ownership/status failure: backend rejects narration submission before worker execution.
- No R2 fallback is attempted for a failed local project-media write.

## Testing

Required coverage:

- narration with preset voice writes final audio to local storage;
- narration with custom voice reads reference from R2 and writes final audio to local storage;
- image generation writes output to local storage regardless of R2 voice configuration;
- project-media workers do not instantiate/use R2 storage for output;
- voice upload keys are account scoped and ownership remains enforced;
- R2 voice validation remains functional;
- project local import/materialization validation remains functional;
- configuration rejects/does not expose an R2 project-media output mode;
- stale R2-specific local narration log assertions are removed/updated.

## Success Criteria

The implementation is complete when a repository-wide search and tests show that R2 is used only for voice-reference/custom-voice storage paths and their validation/download lifecycle, while all project media generation/import/render paths persist locally.
