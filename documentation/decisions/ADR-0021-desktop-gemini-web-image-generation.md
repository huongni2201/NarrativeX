# ADR-0021: Desktop Gemini Web image generation boundary

- Status: Accepted
- Date: 2026-08-28
- Amended: 2026-09-07

## Context

NarrativeX has a backend-authorized Vertex/API image-generation path owned by the durable generation model and Python workers. The Desktop Storyboard also needs a user-driven path that can use the Gemini Web product for one Visual Beat at a time, including a guided Generate All flow.

Gemini Web is a browser product rather than a provider SDK exposed to the backend. Its authentication is user-owned, its page UI can change independently of NarrativeX, and its generated bytes must still enter the local-first project storage boundary with stable backend asset metadata.

Desktop also needs to support more than one user-owned Gemini browser session on the same device. A second browser may use the same Google account or a different account, but login state, Chrome profile data and process/CDP lifecycle must remain isolated. Adding a browser must not multiply configured Character or Storyboard concurrency automatically.

## Decision

1. `GEMINI_WEB` is a Desktop-only image provider path. The Chapter setup records the provider choice, but Images does not create the backend API media job, reuse/reframe plan or API cost estimate for this provider. Storyboard is the generation entry point and always uses `GENERATE_NEW`.
2. Electron main owns Chrome lifecycle and browser automation. Each NarrativeX user has one Gemini browser profile by default and may add more from Desktop Settings. Every browser entry owns an independent Chrome process lifecycle, dedicated `--user-data-dir`, local loopback DevTools Protocol port, target/session metadata and download namespaces. Browser profile roots are device-local and user-local. The renderer never receives Chrome profile paths, CDP ports, cookies, process handles or filesystem capabilities.
3. Each browser host may own multiple reusable Gemini page targets for `CHARACTER` and `STORYBOARD` work. The browser pool composes the existing page/slot automation rather than sharing page targets between browser profiles. Target identity, generation state, CDP/network capture and downloads stay isolated by browser, lane and slot.
4. The user signs in to Gemini in the selected NarrativeX Chrome browser when required. NarrativeX does not fill, read or persist Google/Gemini passwords, OAuth tokens or cookies in Desktop preferences. Chrome-owned cookies and local storage remain inside that browser's persistent profile. Authentication status is derived from the live Gemini UI rather than trusted from a persisted `loggedIn` boolean.
5. Desktop Settings exposes browser management through trusted IPC: list, add, open, login, reset login and remove. At least one browser entry must remain. Resetting or removing a browser with active generation leases is rejected. Reset Login removes only the selected browser's local Chrome/session data. Generic Gemini-concurrency and all-personalization resets do not silently delete browser login profiles.
6. The backend is the sole owner of the exact final Storyboard prompt. Before one-beat or Generate All dispatch, the backend prepares an immutable generation batch that pins source/storyboard/continuity revisions, style/provider policy versions, exact prompt text, character snapshot, ordered reference metadata/checksums and per-beat input fingerprints. The renderer and Electron main submit that prompt verbatim; neither layer appends or rebuilds a parallel style wrapper. Electron main validates that the Storyboard request carries the expected pinned policy versions and provenance before Chrome automation.
7. Generation downloads one full-size image, validates that it is a supported non-empty image, calculates SHA-256 and exposes only metadata plus a short-lived sender-bound, single-use selection token to the renderer. The renderer registers `LOCAL_ONLY` asset metadata through the backend, then invokes the trusted commit capability so main copies the staged bytes into ProjectStorage. The renderer persists that stable media asset as the Visual Beat preview only after stale/provenance checks. An untimed/manual Visual Beat must not lose its preview merely because no production timeline row exists yet.
8. Gemini generation requests carry a required `CHARACTER` or `STORYBOARD` lane discriminator through the typed preload boundary, but they do not carry a browser id. Electron main selects an authenticated, healthy browser automatically. Selection favors the least-active eligible browser and rotates ties fairly. Once an attempt has crossed the dispatch boundary, a failure is surfaced for that attempt and is not silently replayed through another browser/account.
9. Character and Storyboard concurrency are global per-user limits across the entire browser pool, not per-browser multipliers. The built-in defaults remain Character `2` and Storyboard `4`, configurable from `1` to `8`. Adding Browser 2 does not turn Storyboard `4` into `8`. A bounded global lane gate controls total work while each selected browser retains host-local reusable slots.
10. Storyboard Generate All remains a renderer-owned, project/chapter-scoped bounded-parallel executor, but its pending work is no longer defined by live prompt reads. PostgreSQL owns immutable prepared batch/snapshot business metadata; the local queue is an execution-progress cache containing batch/snapshot/attempt identity. Legacy queue payloads are migrated paused and must prepare only pending beats before resuming. Queue state is not a second business authority.
11. Electron main keeps a device-local attempt journal for external-side-effect reconciliation. Attempts are bound to `attemptId`, batch/snapshot IDs and fingerprints. Ambiguous `SUBMITTING`/`UNKNOWN` outcomes are never blindly resubmitted. The renderer also persists a conservative `SUBMITTING` stage before crossing IPC so a renderer crash cannot turn a possibly-submitted attempt back into fresh work if the main journal is unavailable.
12. Stop/pause prevents new submissions but does not promise cancellation of prompts already running in Chrome. In-flight outputs still pass a backend stale check. If source/canon/continuity changes while generation is running, the output may be retained as a local asset for review but must not attach to the newer beat revision.
13. Reference transport is checksum-bound. Prepared snapshots carry ordered reference labels/roles/content type/SHA-256. Renderer materialization is checksum-aware and deduplicates in-flight materialization; Electron main hashes the resolved local bytes again immediately before upload and rejects missing, corrupt, duplicate or reordered reference inputs rather than falling back to another image.
14. Durable image persistence defines a successful Storyboard attachment. Cache invalidation is a handled background refresh and must not turn an attached image into a failed queue item, prevent progress from advancing or cause blind regeneration. A newly attached generated preview resets Visual Beat review status to `NEEDS_REVIEW`; generated media is not implicitly approved.
15. Prompt copy uses a typed preload capability to Electron main's clipboard API. The renderer does not call `navigator.clipboard` or receive a general clipboard primitive.
16. Existing single-browser local data is migrated to the current user's `Browser 1` profile using an idempotent, allowlisted migration of known automation entries. Unknown legacy profile data is never deleted as a side effect of migration.

## Consequences

### Positive

- Users can use existing Gemini Web access without putting provider credentials or a browser editor into the NarrativeX renderer.
- Users can keep multiple independent Google/Gemini sessions on one device and choose the account during manual login without NarrativeX storing credentials.
- One browser remains the zero-configuration default; adding another browser is optional.
- A failed or logged-out browser can be excluded from new scheduling without invalidating other authenticated browser hosts.
- Global Character/Storyboard limits keep resource usage predictable when browser count changes.
- The generated result follows the existing local-first project media contract and backend stable asset identity/checksum rules.
- Immutable backend batches make submitted Storyboard inputs auditable and prevent mixed revisions when bounded-parallel slots become available at different times.
- Attempt identity and conservative UNKNOWN reconciliation prevent blind duplicate submissions across restart/resume/browser selection.
- Selection-token binding and validation keep the privileged file commit outside the renderer.
- Queue progress survives navigation while server-owned snapshot metadata remains authoritative.

### Trade-offs

- Every additional browser profile may add a Chrome browser process plus renderer/helper processes, increasing memory use.
- Chrome installation, per-profile Gemini sign-in state and Gemini's changing web UI are runtime dependencies. Missing Chrome, UI changes, timeouts and failed downloads are user-visible errors rather than durable provider states.
- The browser pool cannot guarantee that Google will keep every login valid indefinitely; expired, revoked or re-verification-required sessions return to a not-logged-in state.
- Gemini Web generation has no API cost estimate or backend provider-operation ledger. The prepared batch and local attempt journal provide input provenance/reconciliation only; they do not pretend Gemini Web is a paid provider API.
- A conservative crash window may produce `UNKNOWN` even when a prompt did not actually reach Gemini. Safety favors manual reconciliation/skip over blind replay.
- Multiple active Gemini tabs/accounts may encounter provider-side throttling. NarrativeX does not evade provider limits or automatically replay submitted work through a different account.
- Provider output quality still varies even when deterministic input/transport correctness is proven; real-image visual evaluation remains a separate release gate.

## Revisit criteria

Revisit this boundary if Gemini publishes a supported API/provider contract that meets the product's cost, quality and continuity requirements, or if Desktop needs durable cross-device batching, usage reconciliation, cancellation guarantees, unattended execution or encrypted cross-device browser-profile synchronization. Any replacement must preserve the main/preload/renderer boundary, immutable input provenance, untrusted scene-input handling and local asset integrity checks.
