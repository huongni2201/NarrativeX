# NarrativeX Compute Protocol v1

## Status

Active Compute Protocol v1 contract. The execution boundary, signed event delivery, idempotent
receipt, and scheduled reconciliation described here are implemented in the current backend and
generation-service paths. This document is not a migration target.

## Boundary

The backend is the control plane. It owns domain interpretation, admission, system capacity checks,
`GenerationJob`, `StageAttempt`, `ProviderOperation`, retries, reconciliation, idempotency, event
receipt state, artifact publication, and all NarrativeX database writes.

`generation-service` is a domain-agnostic execution plane. It accepts a fully materialized compute task,
invokes an executor, stages output artifacts, and reports observations. It must not:

- receive or infer `Project`, `StoryVersion`, `Chapter`, `Scene`, `StoryBeat`, `AudioCue`, `VisualBeat`, character, workspace, or NarrativeX identity IDs;
- connect to the NarrativeX PostgreSQL database;
- resolve NarrativeX domain records or construct domain output;
- decide retry, admission, job completion, or provider reconciliation policy;
- accept or return absolute host filesystem paths.

Local RTX 4060 and remote GPU deployments implement the same versioned HTTP contract. Backend
target configuration changes endpoint, credentials, capabilities, and scheduling weight without
changing a domain use case.

## Concepts

### ComputeTask

A single immutable execution request. A retry is a new `attemptId`; replay of the same attempt is
idempotent. The backend persists its reservation and attempt intent before submission.

```json
{
  "protocolVersion": "1.0",
  "taskId": "0199b861-cc3c-7a8e-a915-e5dbff3af7aa",
  "attemptId": "0199b862-1025-78be-bd71-c6969b74ab71",
  "idempotencyKey": "compute:0199b861-cc3c-7a8e-a915-e5dbff3af7aa:1",
  "requestFingerprint": "0d3c8f5d67c48b0889828cc22b2d51cd9785f51b788350134209d1be1b411285",
  "task": {
    "type": "audio.synthesize",
    "schemaVersion": "1.0"
  },
  "model": {
    "executor": "vieneu",
    "model": "vi-profile",
    "revision": "0.5.2"
  },
  "constraints": {
    "deadline": "2026-09-14T12:00:00Z",
    "maxRuntimeSeconds": 900
  },
  "inputs": {
    "script": "Untrusted story text is data, never worker instructions.",
    "voice": {"kind": "catalog", "value": "vi_female_01"},
    "format": {"container": "wav", "sampleRateHz": 48000, "channels": 1}
  },
  "artifacts": [
    {
      "artifactId": "0199b86a-6db8-75b8-bd98-78442a0177dd",
      "role": "voice-reference",
      "mediaType": "audio/wav",
      "sizeBytes": 382144,
      "sha256": "250c9509df659bdfa83d3e6ba687313ba8100b21e8e6ab2daee3f5f3e9eec945",
      "access": {
        "method": "GET",
        "url": "https://artifact-gateway.example/opaque-capability",
        "expiresAt": "2026-09-14T12:15:00Z",
        "headers": {}
      }
    }
  ],
  "outputTargets": [
    {
      "artifactId": "0199b86a-6db8-75b8-bd98-78442a0177de",
      "role": "audio",
      "mediaType": "audio/wav",
      "access": {
        "method": "PUT",
        "url": "https://artifact-gateway.example/upload-capability",
        "expiresAt": "2026-09-14T12:15:00Z",
        "headers": {}
      }
    }
  ]
}
```

Rules:

- UUIDs are opaque protocol identifiers generated by the backend; they are not domain IDs.
- `requestFingerprint` is SHA-256 over UTF-8 canonical JSON (`sort_keys=true`, no insignificant
  whitespace) containing exactly `protocolVersion`, `task`, `model`, `constraints`, `inputs`, and each input
  artifact's `artifactId`, `role`, `mediaType`, `sizeBytes`, and `sha256`. Protocol/task/attempt/idempotency IDs
  and expiring `access` descriptors (`url`, `headers`, `expiresAt`) are excluded. The same semantic compute
  request therefore keeps its fingerprint across attempts and refreshed artifact capabilities.
- `task.type` selects a versioned input/output schema from the executor registry. Unknown fields
  are rejected by default; an unrestricted `metadata` bag is deliberately absent.
- Story text, prompts, references, and model output remain untrusted data. Executors must treat
  them as typed input and must not interpret them as control-plane instructions.
- Model selection is explicit and immutable for an attempt. A target may reject unsupported
  executor/model/revision combinations but may not silently substitute another model.
- `constraints.deadline` is validated before `ACCEPTED`. If the deadline is already in the past,
  the worker rejects the task with a validation error (`422 Unprocessable Entity`).

The active task types are `audio.synthesize`, `audio.align`, `image.generate`, and `media.validate`.
Add a task type only with schemas, deterministic validation, capability advertisement, tests, and
documented artifact behavior. Chapter analysis is handled directly by Spring Boot using Vertex AI
Gemini 3.8 Flash (ADR-0022) rather than compute-plane text generation. FFmpeg GPU work can later use `media.transcode`.

### Artifact Models

Artifact handling is split into three distinct models to maintain integrity and access boundaries:

#### 1. InputArtifactRef
Identifies input bytes, checksum integrity, role, and a time-bounded read capability (`ArtifactReadAccess`):
```json
{
  "artifactId": "0199b86a-6db8-75b8-bd98-78442a0177dd",
  "role": "voice-reference",
  "mediaType": "audio/wav",
  "sizeBytes": 382144,
  "sha256": "250c9509df659bdfa83d3e6ba687313ba8100b21e8e6ab2daee3f5f3e9eec945",
  "access": {
    "method": "GET",
    "url": "https://artifact-gateway.example/opaque-capability",
    "expiresAt": "2026-09-14T12:15:00Z",
    "headers": {}
  }
}
```

#### 2. OutputArtifactTarget
Identifies expected output slots with a pre-authorized staging upload capability (`ArtifactWriteAccess`):
```json
{
  "artifactId": "0199b86a-6db8-75b8-bd98-78442a0177de",
  "role": "audio",
  "mediaType": "audio/wav",
  "access": {
    "method": "PUT",
    "url": "https://artifact-gateway.example/upload-capability",
    "expiresAt": "2026-09-14T12:15:00Z",
    "headers": {}
  }
}
```

#### 3. ProducedArtifact
Reported in `ComputeObservation.outputs` upon successful execution. Contains computed integrity metadata:
```json
{
  "artifactId": "0199b86a-6db8-75b8-bd98-78442a0177de",
  "role": "audio",
  "mediaType": "audio/wav",
  "sizeBytes": 482910,
  "sha256": "3a8c62b489a5ee010dcda59a60fae248b112d8a0be4f30dc9e5f9a6566089862"
}
```

The worker downloads input artifacts using the read capability, executes the model, uploads outputs to the staging target capability, computes and verifies the byte count and SHA-256 digest locally, and reports the verified `ProducedArtifact` in the observation; the backend verifies and atomically publishes it before completing domain state.

Local deployments may implement the artifact gateway over loopback, but the wire contract remains
an opaque URL/capability. `file://`, drive letters, UNC paths, project-relative storage keys, and
host absolute paths are invalid protocol values.

### ComputeResult

```json
{
  "protocolVersion": "1.0",
  "taskId": "0199b861-cc3c-7a8e-a915-e5dbff3af7aa",
  "attemptId": "0199b862-1025-78be-bd71-c6969b74ab71",

  "sequence": 7,
  "observedAt": "2026-09-14T11:42:31Z",
  "executionHandle": "opaque-to-backend-and-logs",
  "outputs": [],
  "metrics": {
    "runtimeMs": 18321,
    "gpuTimeMs": 17104,
    "peakVramBytes": 6442450944
  }

```

### Execution Handles and Checkpoints

The optional `executionHandle` in `ComputeObservation` represents an opaque identifier issued by or for the executor (such as an external engine prompt/job ID, batch handle, or process checkpoint).

- **Durable storage**: Stored durably in the worker SQLite journal alongside the attempt state.
- **ExecutionContext**: The application service passes an `ExecutionContext` to executors containing:
  - `task_id`, `attempt_id`, `work_dir`
  - `deadline`, `max_runtime_seconds`
  - `cancel_requested_fn()`: synchronous/asynchronous callback to poll durable cancellation state
  - `save_handle_fn(handle)`: callback to persist updated checkpoint handle to the journal
  - `existing_handle`: restored handle when resuming an execution attempt after a worker restart
- **Redaction**: Execution handles are opaque and redacted from user-facing logs and error details.

### Error Contract and Deadlines

Terminal failure uses a bounded, non-sensitive error contract:

```json
{
  "state": "FAILED",
  "error": {
    "code": "INVALID_INPUT",
    "category": "PERMANENT",
    "message": "Input audio is not a valid WAV stream",
    "retryAfterSeconds": null,
    "details": {}
  }
}
```

Allowed categories are `PERMANENT`, `TRANSIENT`, `CAPACITY`, and `CANCELED`. They are observations,
not retry decisions. Backend policy chooses whether and when to create another attempt. Error
messages and details must not contain prompts, secrets, signed URLs, provider response bodies, or
local paths.

#### Timeout vs Deadline Exceeded

The worker distinguishes between overall execution deadlines and individual execution timeouts:

- `DEADLINE_EXCEEDED` (`category: PERMANENT`):
  - Emitted when `constraints.deadline` expires.
  - Validated prior to `ACCEPTED` admission (returns HTTP 422 if already in the past).
  - Validated on worker recovery/restart: if a recovered task's deadline has already elapsed, the attempt is transitioned immediately to `FAILED` with `DEADLINE_EXCEEDED` without executing.
- `EXECUTION_TIMEOUT` (`category: TRANSIENT`):
  - Emitted when the attempt runtime exceeds the effective timeout computed from `min(deadline - now, maxRuntimeSeconds)`.

## HTTP contract

All media types are `application/vnd.narrativex.compute-v1+json`. Mismatches are rejected with `415 Unsupported Media Type`. Streaming request body sizes exceeding configured worker thresholds are rejected with `413 Content Too Large`.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/v1/capabilities` | Worker identity, protocol versions, executors/models, task schemas, limits and health summary |
| `POST` | `/v1/tasks` | Submit an immutable attempt; return `202 Accepted` or the stored replay response |
| `GET` | `/v1/tasks/{taskId}/attempts/{attemptId}` | Reconcile after timeout or ambiguous submission |
| `POST` | `/v1/tasks/{taskId}/attempts/{attemptId}:cancel` | Request cooperative cancellation; idempotent |
| `POST` | backend callback URL `/internal/compute/events` or `/internal/v1/compute-events` | Deliver signed sequenced observations |

`POST /v1/tasks` must return the same acceptance/result for the same `attemptId`, idempotency key,
and fingerprint. Reusing one of those identifiers with a different fingerprint returns `409
Conflict`. Unsupported protocol/task/model combinations return `422`; temporary capacity returns
`429` with `Retry-After`; authentication/authorization uses `401`/`403` without revealing target
configuration.

## Event Delivery and Reconciliation (ADR-0025)

The worker and backend use a durable event path in addition to the reconciliation endpoint:

```text
worker execution state transition
  -> SQLite transaction updates execution_attempts
  -> same transaction appends compute_event_outbox(event_id, attempt_id, sequence, payload)
  -> OutboxDeliveryService retries delivery with bounded backoff
  -> HMAC-signed POST to /internal/compute/events or /internal/v1/compute-events
  -> backend verifies signature and timestamp
  -> compute_event_receipts records event_id once
  -> common finalizer applies monotonic state transition
  -> project-scoped SSE emits job.updated / job.completed / job.failed
```

Callback signing uses HMAC-SHA256 over `${timestampHeader}.${rawBody}` with the machine secret.
The worker sends `X-NarrativeX-Compute-Signature` and `X-NarrativeX-Compute-Timestamp`; the
backend accepts millisecond or ISO timestamps and rejects timestamps outside the five-minute
replay window. The raw body is verified before deserialization. A duplicate `event_id` is
acknowledged without reprocessing, and an event older than the current attempt sequence is a
monotonic no-op.

Transaction boundaries are deliberate: backend intent is committed before external submission;
remote worker/provider I/O happens outside backend database transactions; the callback receipt and
finalization transaction performs local PostgreSQL work only; reconciliation performs one remote
observation outside a transaction and then persists it in a short local transaction. No long
database transaction contains external I/O.

`ComputeReconciliationScheduler` runs a bounded, non-blocking worker query for due
`SUBMITTED`, `RUNNING`, `UNKNOWN`, and `RECONCILING` attempts. It uses the same finalizer as the
callback path and backs off after failures. It is the source-of-truth fallback for lost callbacks
and ambiguous submission outcomes, not a second state machine.

Desktop subscribes to `GET /api/v1/projects/{projectId}/generation/events` through the Electron
bridge. SSE events invalidate generation, Chapter, timeline, and storyboard queries; reconnect
and terminal snapshots are handled by the Desktop transport.

### Cancellation Semantics

`POST /v1/tasks/{taskId}/attempts/{attemptId}:cancel` initiates cooperative cancellation.

1. **Journal-before-memory flow**: The worker persists `cancel_requested = 1` in its SQLite execution journal before canceling running in-memory tasks.
2. **Terminal state immutability**: If an attempt has already reached a terminal state (`SUCCEEDED`, `FAILED`, or `CANCELED`), the cancel request is a safe no-op and returns the existing observation without altering terminal state.
3. **Controlled shutdown**: Graceful worker shutdown or task interruption does NOT persist cancellation. Interrupted attempts remain in `ACCEPTED` or `RUNNING` in the journal, allowing them to be safely recovered and resumed or reconciled upon worker restart.

### Lifecycle & State Transitions

Callbacks and reconciliation share the same finalizer. Every observation carries a monotonically
increasing `sequence`; duplicate event IDs and older sequences are accepted as no-ops. The minimal
execution states are:

```text
ACCEPTED -> RUNNING -> SUCCEEDED
                    -> FAILED
                    -> CANCELED
```

Loss of acknowledgement or transport does not itself produce an execution state. The backend maps
that ambiguity to durable `ProviderOperation.UNKNOWN` and reconciles before resubmitting. A worker
restart must recover accepted/running attempts from its own execution journal; that journal is
execution-local and contains no NarrativeX domain data.

## Security and operational requirements

- Authenticate each target using a separate machine credential; prefer mTLS for remote targets and
  bind local workers to loopback/private interfaces. Rotate credentials independently of provider
  browser state.
- Authorize callback events to one target identity and reject task/attempt mismatches.
- Never pass `DATABASE_URL` or NarrativeX service credentials to `generation-service`.
- Enforce request size, artifact size, media type, checksum, decompression, runtime, output count,
  concurrency, and model allow-list limits before execution.
- Redact prompt/input content, signed artifact URLs, voice references, provider bodies, and execution
  handles from logs. Correlate by `taskId` and `attemptId` only.
- Capability discovery is cached for routing but cannot override the backend model/target registry.
- Readiness means the configured executor/model can accept work; fake executors are test-only and
  must never report production readiness.

## Ownership mapping

| Concern | Backend control plane | GPU execution plane |
|---|---|---|
| Domain context and materialization | Owns | Forbidden |
| Admission, system capacity, and abuse checks | Owns | Enforces only local safety/capacity limits |
| Job/attempt/provider lifecycle | Owns durable truth | Reports execution observations |
| Retry and `UNKNOWN` reconciliation | Decides and persists | Returns idempotent status by attempt |
| Model and target registry | Owns desired configuration | Advertises actual capabilities |
| Artifact identity/publication | Coordinates and verifies | Downloads/uploads through capabilities |
| Provider/engine SDKs | Forbidden from domain modules | Executor adapters own them |
| NarrativeX PostgreSQL | Owns | Forbidden |
| Single-GPU model residency & arbitration | Unaware | Owns via `GpuResidencyManager` |

## Compatibility

Minor additions may add optional fields or task schemas without changing existing semantics. Any
renamed field, changed state meaning, changed fingerprint rule, or changed artifact behavior requires
a new major media type and a parallel compatibility window. Backend and worker contract tests use a
shared checked-in JSON Schema/OpenAPI source and golden examples.
